Getting Started with the Operator API

The Operator API lets a ferry operator's own system — a booking engine, a ticketing website, a sales counter app — check passengers in to the operator's trips without anyone retyping them in the Operator Portal. These pages are for the developers building that connection.

What you want to doEndpointPermissionGuide
Check a passenger in and get their boarding pass numberPOST /api/Operator/Passengers/by-codeoperator.passenger.writeCheck In a Passenger
Cancel a check-inPATCH /api/Operator/Passengers/cancel-by-codeoperator.passenger.cancelCancel a Check-in
List every passenger on a trip with their statusGET /api/Operator/Passengers/by-tripoperator.passenger.readGet Passenger Statuses
Server to server only

Call the API from your server. Browsers are blocked — the API accepts browser requests only from the Opusbay portals. Never put the integration account's password in a web page or a mobile app.

Swagger

The same endpoints, with their request and response schemas, are in Swagger at {API_BASE_URL}/swagger — choose Operator API v1 in the definition list at the top right.

Set up the integration account​

Use a dedicated account for the integration, not a person's account. It signs in like any other user, so it is set up the same way:

  1. Register it with a mailbox your team controls, and confirm the email — see Register an Account.
  2. Your Operator Portal administrator adds it as a user with exactly that email — see Add a New User — and a Super Admin activates it — see Activate or Deactivate a User.
  3. Give it the three permissions through a role — see Add a New Role, Manage a Role's Permissions and Assign a Role to a User:
    • operator.passenger.write — check in
    • operator.passenger.cancel — cancel a check-in
    • operator.passenger.read — list passenger statuses
Don't make it an Admin

An Admin passes every permission check, so a leaked password would expose far more than passenger check-in. Grant only the three permissions above.

Get an access token​

Sign in with the account's email and password. URL-encode both values in the form body.

POST {API_BASE_URL}/token
Content-Type: application/x-www-form-urlencoded

grant_type=password&client_id=opusbay-ts-api&username={email}&password={password}
{ "access_token": "eyJhbGciOi…", "expires_in": 3600, "token_type": "Bearer" }

Send the token on every call as Authorization: Bearer {access_token}. It expires after expires_in seconds. The lifetime is set per environment, so always read the value rather than assuming one. Keep the token and reuse it until shortly before it expires, then sign in again with the same request. Don't sign in before every call.

There is no refresh token: this client never issues one, so signing in again is how you renew.

A wrong email or password returns 400 with {"error":"invalid_grant","error_description":"Incorrect email or password."}. How Sign-In and Access Work explains how a sign-in account and an operator user fit together.

Limits
  • /token accepts 10 requests per minute per public IP address, shared by everything behind that address. Over the limit it returns 429.
  • 10 wrong passwords in a row lock the account for 15 minutes. Every renewal is a sign-in, so when one fails, stop and alert someone instead of retrying in a loop.

Send these headers​

HeaderValue
AuthorizationBearer {access_token}
X-Operator-CodeYour operator code, for example OP001
Content-Typeapplication/json — on POST and PATCH

Every call acts for the operator in X-Operator-Code. The integration account must be an active user of that operator, and it only ever sees and changes that operator's trips and passengers.

Identify the trip​

You never send a trip id. Every call names the trip by the parts of its trip code instead:

FieldFormatExampleNotes
tripTypeinteger00 Scheduled (generated from a timeslot), 1 AdHoc (a one-off trip).
routeTripCodestring"HW"The route's trip code.
tripDateyyyy-MM-dd"2026-11-02"The sailing date, in the departure port's local time.
departureHH:mm:ss, 24-hour"09:30:00"The scheduled departure, in the departure port's local time.
suffixstring, optionalnullOnly for a trip whose code ends with a suffix. Otherwise leave it out.

The API builds the trip code from these parts, plus your operator's own trip code, which it takes from X-Operator-Code:

PartExampleComes from
TypeStripType: S for Scheduled, A for AdHoc
Operator trip codeSFYour operator — never sent
Route trip codeHWrouteTripCode
Date20261102tripDate
Time0930departure, hours and minutes
Suffix—suffix, when the trip has one

Together: SSFHW202611020930. The same code is shown on every trip in the Operator Portal — in the Departure Trips grid and on the trip's detail page, see Look Up a Trip. Reading it backwards is the quickest way to find a route's trip code or a trip's suffix. A suffix exists only when two trips would otherwise share a code — same route, date and departure time.

A delay does not change the code

When the terminal records a delay, the trip keeps its scheduled departure in its code. Always send the scheduled time, not the delayed one.

Debugging a 404

When no trip matches, the error message names the code the API looked for — for example Departure trip not found (code 'SSFHW202611021000'). Compare it with the code in the Operator Portal to see which part is wrong.

Data formats​

  • Request and response bodies are JSON, with camelCase field names.

  • Dates are yyyy-MM-dd and times are 24-hour HH:mm:ss, with no time zone. A trip's date and departure are in the departure port's local time.

  • Enumerations are integers:

    FieldValues
    tripType0 Scheduled, 1 AdHoc
    gender0 Male, 1 Female, 2 Unspecified
    status (passenger)0 CheckedIn, 1 PreImmigration, 2 Boarded, 3 Cancelled

Errors​

Errors raised by the endpoints themselves share one envelope:

{
  "exception": {
    "type": "UserFriendlyException",
    "message": "No available seats on this trip.",
    "errors": null,
    "traceId": "0HNG4A8V3KQ1E:00000003",
    "statusCode": 400,
    "stackTrace": null
  }
}
HTTPtypeMeaning
400ValidationExceptionOne or more fields are invalid. errors lists the messages per field, for example {"No": ["A passenger with this No already exists on this trip."]}.
400UserFriendlyExceptionA business rule refused the request. Read message.
404NotFoundExceptionThe trip, passenger or country wasn't found. Read message.
500variesSomething unexpected. message is An unexpected error occurred.

Show message to your staff, and quote traceId when you report a problem.

Some requests are refused before they reach the endpoint, with a different body:

HTTPWhenBody
400X-Operator-Code is missing or empty. Checked first, even before the token.{"error":"X-Operator-Code header is required"}
404X-Operator-Code isn't an active operator.{"error":"Operator not found"}
401The access token is missing, invalid or expired.empty
403The account isn't an active user of that operator.User not registered in this Operator.
403The account lacks the endpoint's permission.empty
400The body isn't valid JSON, a required field is missing, or a value has the wrong format.A validation problem (application/problem+json) with title, status and errors.
What to do with an error
  • 401 — get a new token, then retry once.
  • 400, 403 or 404 — don't retry unchanged; fix the request or the account.
  • 500 or a timeout — retrying is safe. Each guide explains what a retry returns if the first attempt had in fact succeeded.
