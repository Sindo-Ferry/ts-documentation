Generate Departure Trips with a Trip Sync Job

This guide walks terminal staff through generating ferry departure trips in the Terminal Portal:

Trip Sync Job → Create New Sync Job → Execute Job → Departure Trips

A Trip Sync Job reconciles the scheduled departure trips for a date range against the active timeslots. When you execute it, the portal creates a departure trip for every active timeslot that matches the job's operator, route, and days on each date in the range (and removes trips that should no longer exist), so the generated trips become visible in Departure Trips.

note

You need an account with permission to manage trip synchronizations. The screenshots below use https://ts-terminal.sindoferry.com.sg/.

Prerequisites​

  • You are signed in to the Terminal Portal — see Sign In to the Terminal Portal.
  • Permission to view and manage Trip Synchronizations and Departure Trips.

Step 1 — Open Trip Sync Jobs​

In the sidebar under Management, open Trip Sync Jobs (route: /departure-trip-synchronizations). The page itself is headed Trip Synchronizations and lists previous sync jobs, one row each:

ColumnShows
Date RangeThe period the job covers (with the job's remark beneath it)
Operator / RouteThe job's scope — All when left blank
Results+N created and −N deleted
StatusPending, Enqueued, or Completed
Requested ByWho created it, and when

Use Show Filters to narrow the list, and New Sync Job (top right) to start one.

The Trip Synchronizations list — past jobs with their scope, results, and status, and the New Sync Job button.

Trips are also synced automatically every day

Alongside the jobs you run by hand, the system runs its own sync once a day. It appears in this list as Requested By: System (Daily Auto-Sync), with a remark like "Automated daily rolling sync from 29-Sep-2026 to 29-Oct-2026".

The automatic job covers a rolling window 60 to 90 days ahead, across all operators, all routes, and all days (public holidays included). It is created and executed straight away — there is no preview to approve.

This is why trips usually already exist for dates a couple of months out, and why a manual job for a near date often previews 0 to create. Run a job by hand when you need trips sooner than the automatic window reaches, or when you have just changed a timeslot and want the trips rebuilt now.

Step 2 — Create a new sync job​

Click New Sync Job (top right) and fill in the job configuration:

  • Start Date / End Date — the period to generate trips for (use the same day for a single date).
  • Operator (optional — leave blank for all) — clicking it opens a Select Operator picker: search the table, then Select the operator's row. Only active operators are listed.
  • Route (optional — leave blank for all) — leave as All Routes to include every route.
  • Day Filter (optional — leave unchecked for all) — Weekdays and Weekends tick their days in one click, and Clear All resets them. Ticked weekdays include those days of the week; P.H. additionally includes every date that is a public holiday (in any country).
  • Remarks (optional) — a note describing the job's purpose.

Then click Create Sync Job.

Date rules

The Start Date cannot be in the past, and the End Date must be on or after the Start Date.

The New Sync Job form — a date range, an optional operator/route scope, and the day filter.

Step 3 — Review the preview and execute the job​

Creating the job opens its detail page, headed Sync Job — start → end with its status badge and who created it. The page has three sections:

1. Job Configuration — the same fields you just filled in, still editable while the job is Pending. Correct anything with Save Changes, or scrap the job with Delete Job.

2. Preview — three counts, To Create, To Delete, and Conflicts. Below them, Trips to Create lists every trip the job will generate, grouped by date, then by route, with each individual departure showing its time and operator. Expand a date or a route to drill in and check the detail before committing. Refresh Preview (top right) re-runs the comparison if the underlying timeslots or trips have changed since the job was created.

3. Execute — when the preview looks correct, click Execute Job. A confirmation asks "Execute synchronization job?" and repeats that trips will be created and deleted as shown in the preview and that conflicts will be skipped. Click Execute.

The job is then enqueued and processed in the background; its status moves from Pending → Enqueued → Completed. Reload the page to see the final counts.

The preview — To Create / To Delete / Conflicts, with the trip list expanded by date and route, and Execute Job below.

Only pending jobs can be changed

Edit, Delete, and Execute apply only while a job is Pending. Once it is Enqueued or Completed the actions are no longer offered — a completed job is a record of what ran. To sync the same period again, create a new job.

Reading the preview

The preview compares each date's active timeslots against the existing Scheduled trips and buckets the difference into three results:

  • To Create — an active timeslot has no matching trip yet on that date.
  • To Delete — a scheduled trip no longer matches any active timeslot and has no check-ins or boarded passengers, so it is safe to remove.
  • Conflicts — an orphaned trip already has passengers / check-ins; it is skipped (never deleted) and flagged for manual review.

So 0 to create / 0 to delete / 0 conflicts means everything is already in sync — the job is idempotent and safe to re-run.

Step 4 — Verify the trips in Departure Trips​

Open Departure Trips (route: /departure-trips/list). Filter the Trip Date to the period you just synced to see the generated trips, each with its code, operator, route, departure time, status, and passenger counts.

Type = Scheduled

Every trip generated by a Trip Sync Job has Type = Scheduled. One-off trips added manually are AdHoc instead — see Departure Trips.

The generated trips for the synced period, each with Type = Scheduled.

What happens during a sync​

The job only ever affects Scheduled trips — AdHoc trips are never touched.

Which timeslots run on a date​

The day rule is additive — a public holiday adds sailings and never removes the weekday ones:

The date is…A timeslot runs when…
any dateits weekday flag for that day of the week is ticked
also a public holiday in country Xadditionally, its Public Holiday countries include X

For example, with a Singapore holiday falling on a Monday: every timeslot with Monday ticked runs as normal; a Public Holiday (SG) timeslot runs as well — an extra sailing that day; a Public Holiday (ID)-only timeslot does not, because the date is not an Indonesian holiday. A timeslot with both Monday and Public Holiday (SG) ticked still generates only one trip that day.

How trips are reconciled​

For each date in the range (subject to the Day Filter), the job compares the timeslots that run on that date — considering only active timeslots whose operator is also active — against the existing scheduled trips, matching them by trip code (operator + route + date + departure + suffix):

ResultWhen it happensWhat execution does
CreatedAn active timeslot applies to that date but has no matching trip yet.A new Scheduled trip is created from the timeslot (with its vessel and gate times).
DeletedA scheduled trip no longer matches any active timeslot (orphaned) and has no check-ins or boarded passengers.The orphaned, empty trip is removed.
ConflictsAn orphaned scheduled trip has check-ins or boarded passengers.It is skipped (kept) and logged for manual review — reassign or clear the passengers, then re-run.
What makes a trip "orphaned"

A trip becomes orphaned when nothing generates it anymore — for example its timeslot was deleted or deactivated, its operator was deactivated, or a holiday-added trip's public holiday entry was deleted (or its timeslot's holiday countries no longer include it). Orphaned trips are then deleted if empty, or raised as a conflict if they already have passengers.
