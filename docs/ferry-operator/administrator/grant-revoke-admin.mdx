The **Admin** flag is not a role. It is an override that gives a user **full access
to everything**, ignoring their roles and permissions entirely.

> **Users → ⋯ → Grant Admin / Revoke Admin → Confirm**

**Permission needed:** `operator.security.is_super_admin`

:::danger[Admin bypasses every permission check]
The confirmation says it plainly: granting admin gives the user _"full access to all
system features, **bypassing standard role restrictions**."_

Nothing you configure with [roles](/operator-administrator/add-role) or
[direct permissions](/operator-administrator/manage-user-permissions) limits an Admin. Grant it
only where someone genuinely needs to administer the portal — not as a shortcut
when a role is fiddly to get right.
:::

:::note
You need the permissions named above. The screenshots below use `https://ts-operator.sindoferry.com.sg/`.
:::

## Before you start

- You are signed in to the Operator Portal — see
  [Sign In to the Operator Portal](/ferry-operator/sign-in).
- You are a **Super Admin**. Ordinary administrators see the menu item disabled.

## Step 1 — Find the user

Open **Users**. Existing administrators carry an **Admin** badge in the
**Status** column; the system owner carries an amber **Super Admin** badge.

## Step 2 — Grant or revoke

Two routes, same dialog:

- **From the list** — the row's **⋯** menu → **Grant Admin** or **Revoke Admin**.
- **From the user's profile** — **⋯ → Manage Security** opens the **User Security
  Profile**, which shows **Admin Access: Enabled / Disabled** and a matching
  **Grant Admin** / **Revoke Admin** button. The button is disabled on the Super
  Admin's own profile.


## Step 3 — Confirm

**Granting:**

> **Grant Administrator Privileges?** — This will grant **[username]** full access to
> all system features, bypassing standard role restrictions.

**Revoking:**

> **Revoke Administrator Privileges?** — This will remove administrative overrides
> for **[username]**. They will revert to standard role-based access.

Click **Confirm Grant** / **Confirm Revoke**.

## What changes

| | Granting | Revoking |
| --- | --- | --- |
| Access | Everything, immediately | Falls back to their roles and direct permissions |
| Roles | Untouched — still assigned, just irrelevant while Admin | Become effective again |
| Badge | **Admin** appears on their row | Disappears |

:::warning[Revoking can strip someone bare]
A user who was made an Admin **before** anyone assigned them roles has no
underlying access at all. Revoke the flag and they fall back to nothing — they can
sign in and see almost nothing.

Before revoking, open their **Roles** tab and check they have something to fall back
on. See [Assign a Role to a User](/operator-administrator/assign-role).
:::

## Admin vs. Super Admin

| | **Admin** | **Super Admin** |
| --- | --- | --- |
| What it does | Full access to portal features | Full access **plus** the security controls — role permissions, user roles, direct permissions, and granting admin |
| How it is set | Granted here by a Super Admin | Not settable from the portal |
| Can be revoked | Yes | **No** — _"Super Admin's administrator priviledges cannot be revoked."_ |
| Can be deactivated | Yes | **No** |
| Can be deleted | Yes, once inactive | **No** |

The Super Admin is the system owner account. It exists so the portal can never lock
itself out of its own administration, which is why none of the destructive actions
apply to it.

:::info[Why the security pages need Super Admin]
[Role permissions](/operator-administrator/manage-role-permissions),
[user roles](/operator-administrator/assign-role) and
[direct permissions](/operator-administrator/manage-user-permissions) all gate their action
buttons on Super Admin — so an ordinary Admin can run the portal but cannot quietly
widen their own access.
:::
