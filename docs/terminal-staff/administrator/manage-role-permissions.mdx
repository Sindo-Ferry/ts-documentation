This is where a role stops being an empty label and starts granting access.

> **Roles → ⋯ → Manage Permissions → tick → Add Selected / Remove Selected**

**Permission needed:** `terminal.security.is_super_admin`

:::warning[Only a Super Admin can change a role’s permissions]
The buttons in both panels are gated on **`terminal.security.is_super_admin`** — not
on `terminal.roles.write` or `terminal.users.write`.

So an ordinary administrator can **open this page and read it**, but the action
buttons will not appear for them. If you can see the lists but not the buttons, that
is why.
:::

:::note
You need the permissions named above. The screenshots below use `https://ts-terminal.sindoferry.com.sg/`.
:::

## Before you start

- You are signed in to the Terminal Portal — see
  [Sign In to the Terminal Portal](/terminal-staff/sign-in).
- The [role exists](/terminal-administrator/add-role).
- You are a **Super Admin**.

## Step 1 — Open the role's permissions

Open **Security → Roles**, find the role, and use its **⋯** menu → **Manage
Permissions** (route: `/roles/permissions?id=…`).

The page is headed **Manage Role Permissions** with the role's name beneath it.
**Check that name before you touch anything** — the two panels look identical
whichever role you opened.

## Step 2 — Understand the two panels

| Panel | What it holds |
| --- | --- |
| **Available Permissions** (left) | Every permission the role does **not** currently have. |
| **Assigned to Role** (right) | Everything the role **does** have. Shown on a tinted background. |

Permissions appear as **raw permission strings** in monospace — for example
`terminal.departure_trip.read`, `terminal.passenger.write`. They are not translated into
friendly names, so read them carefully.

Both panels work the same way:

- **Filter box** — type to narrow the list. With hundreds of permission strings,
  this is the only practical way to find one.
- **Tick the rows** you want. The **checkbox in the header** ticks everything
  currently shown.
- The action button shows the count — **Add Selected (3)** — and stays **disabled
  until at least one row is ticked**.
- Each panel scrolls independently; the selection clears after every action.

## Step 3 — Add permissions

In **Available Permissions**, filter and tick what the role needs, then click
**Add Selected (N)**.

The row moves to **Assigned to Role** and both panels refresh.

:::tip[Read the permission string as three parts]
`terminal.departure_trip.cancel` is _portal_ . _thing_ . _action_. Filtering on the middle
part — type `departure_trip` — gathers everything about one area, which is usually
how you want to grant access.

Watch for the action on the end: `.read` is harmless, `.write`, `.cancel` and
`.execute` are not.
:::

## Step 4 — Remove permissions

In **Assigned to Role**, tick the rows and click **Remove Selected (N)**.

:::warning[Removing takes effect for everyone holding the role]
There is **no confirmation dialog** on either panel. The change applies the moment
you click, and it applies to **every user who holds this role** — potentially mid-shift.

Removing a scan permission from _Boarding Gate Officer_ stops every boarding officer
scanning. Make changes like that between shifts.
:::

## If a change is rejected

| Message | What it means |
| --- | --- |
| _"Invalid permissions detected: …"_ | A permission string that the system does not recognise was submitted. This should not happen from the UI; report it. |

## How role permissions reach a user

A user's **effective** access is the union of:

1. every permission from **every role** they hold, plus
2. any [direct permissions](/terminal-administrator/manage-user-permissions) granted to them
   individually.

You can see the combined result on the user's security profile under the
**Effective Access** tab.

:::info[Admin bypasses all of this]
A user flagged as **Admin** has full access regardless of roles or permissions — see
[Grant or Revoke the Admin Role](/terminal-administrator/grant-revoke-admin). If someone can do
something the role does not allow, check whether they are an Admin before debugging
the role.
:::
